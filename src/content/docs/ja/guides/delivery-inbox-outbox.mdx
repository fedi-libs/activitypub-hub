---
title: Inbox と Outbox
description: サーバー間通信におけるメッセージの配送、受信、および共有インボックス（Shared Inbox）の役割について。
---

ActivityPub のサーバー間（S2S）プロトコルでは、メッセージの交換は主に **Inbox** と **Outbox** という2つのエンドポイントを通じて管理されます。

## メッセージの配送 (Outbox)
:::note[アクティビティの削除と取り消し]

ActivityPub において「削除」を扱う場合、主に2つのアプローチがあります。

##### 1. Delete アクティビティ
すでに配送済みのアクティビティやオブジェクトを削除する場合、`Delete` アクティビティを送信します。
* **Tombstone (墓標)**: 受信側サーバーは、完全にデータを消去する代わりに、その ID が削除されたことを示す `Tombstone` オブジェクトに置き換えることが一般的です。これにより、後から同じ ID で取得を試みた際に 410 Gone を返せるようになります。

##### 2. Undo アクティビティ
`Follow` や `Like`、`Announce`（リポスト）など、特定のアクションを取り消す場合は `Undo` アクティビティを使用します。
* **整合性**: `Undo` の `object` には、取り消したい元のアクティビティをそのまま含める必要があります。受信側は、その `Undo` を送信したアクターが、元のアクティビティの作成者と一致しているかを必ず検証しなければなりません。
:::

純粋な S2S の文脈において、**Outbox** はアクターのアクティビティの正式な起点、いわば「送信済みフォルダ」として機能します。サーバーが新しいアクティビティ（`Create` や `Announce` など）を生成すると、それは概念的にアクターの Outbox に追加され、そのアクターの送信履歴を構成します。

### 配送プロセス
アクティビティが生成されると、サーバーは関連するピアに通知するための配送プロセスを開始します。

1.  **宛先の特定**: サーバーは `to`、`cc`、`audience` フィールド、およびアクターの `followers`（フォロワー）リストを確認し、リモートの受信者の `inbox` URL を特定します。
2.  **送出**: 特定された各リモート `inbox` に対して、サーバーはアクティビティを HTTP POST します。

## メッセージの受信 (Inbox)

**Inbox** は、外部サーバーから送信されたアクティビティを受け取るための専用エンドポイントです。

1.  **アクティビティの受信**: 外部サーバーが、アクターの `inbox` URL に対して `Activity` を POST します。
2.  **検証と処理**: 受信側サーバーは、リクエストの正当性を（HTTP 署名などを通じて）検証します。有効な場合、アクティビティはデータベースへの保存や、ローカルユーザーへの通知トリガーなどの処理に回されます。

## 共有インボックス (Shared Inbox)

アクターに膨大なフォロワー（数千から数百万人）がいる場合、個々のフォロワーの `inbox` すべてに POST を行うと、莫大なオーバーヘッドが発生します。**共有インボックス（Shared Inbox）** は、この大量配送を最適化するための仕組みです。

* **メカニズム**: 同じリモートインスタンスに複数のフォロワーが存在する場合、送信側サーバーはそのインスタンスが定義する `sharedInbox` エンドポイントに対して、アクティビティを **1回だけ** POST します。
* **内部配送**: 受信側サーバーは、その単一の POST を受け取り、内部的に関連するすべてのローカルユーザーへアクティビティを分配します。

この仕組みにより、ネットワークトラフィックが大幅に削減され、送信側・受信側双方のサーバーの CPU やメモリの使用量を最小限に抑えることができます。
