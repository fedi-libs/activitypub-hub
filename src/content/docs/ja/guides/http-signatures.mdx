ActivityPubでは、送信元の正当性を証明するために **HTTP 署名 (HTTP Signatures)** が使用されます。
これは、ActivityPub の公式仕様書（W3C）には詳細が記述されていないものの、実装上は不可欠な要素です。

## 署名の役割

受信側サーバーは `Inbox` に POST されたアクティビティが、本当に送信元のアクターによって作成されたものかどうか、また途中で改ざんされていないかを検証する必要があります。

1.  **認証**: どのアクターがリクエストを送信したかを確認します。
2.  **整合性**: リクエストボディ（アクティビティ）やヘッダーが変更されていないことを確認します。

## 4つの署名方式

Fediverse では、主に以下の4つの方式が使われています。

### 1. Cavage HTTP Signatures (`Draft`)
Mastodon をはじめとする多くの既存実装で採用されている、初期のドラフト仕様です。
- **特徴**: `Signature` ヘッダーに `keyId`、`algorithm`、`headers`、`signature` を含めます。
- **署名対象**: 通常、`(request-target)`、`host`、`date`、`digest` ヘッダーが含まれます。
- **注意点**: RFCとして正式に採択されておらず (下で解説するRFC 9421に置き換えられました)、実装によって細かい差異（仕様への厳格さ）がある場合があります。

### 2. HTTP Message Signatures (`RFC 9421`)
新しく標準化された、より厳密で柔軟な署名方式です。

:::note
RFC 9421は多くの実装との互換性がないため、現在はRFC 9421での署名が正しく認識されなかった場合に上記で解説したCavage HTTP Signaturesをフォールバックとして使用する (Double-Knocking)ことを推奨します。 (MastodonやFedifyがそのような方法を採用しています。)
:::

- **特徴**: `Signature` ヘッダーに加えて、`Signature-Input`ヘッダーも使用します。Cavage HTTP Signaturesとの互換性はなく、同時に使用することもできません。

### 3. Linked Data Signatures 1.0 (`RsaSignature2017`)
Mastodonがリレーからアクティビティを受け入れる場合や自己破壊を実行する際など、上記の2つのHTTP署名が使用できない場合に使用する署名方式です。

### 4. Object Integrity Proofs (`FEP-8b32`)

## 署名の検証プロセス

受信側サーバーがリクエストを検証する際、以下の手順を踏みます。

1.  **リクエストの解析**: `Signature`（または `Signature-Input`）ヘッダーから `keyId` を取得します。
2.  **公開鍵の取得**: `keyId` に紐付くアクターの公開鍵（`publicKey`）を、ネットワーク越しに GET して取得します。
3.  **署名の検証**: 取得した公開鍵を使って、リクエストヘッダーから再構築した署名対象文字列と、送られてきた署名が一致するかを計算します。

## Digest ヘッダーの重要性
ボディ（JSON データ）の改ざんを防ぐため、ボディのハッシュ値を `Digest` ヘッダーに含め、その `Digest` ヘッダーを HTTP 署名の対象に含めるのが一般的です。

これら 2 つの署名方式の共存や、公開鍵のキャッシュ戦略などが、安定したフェデレーション実装の鍵となります。
